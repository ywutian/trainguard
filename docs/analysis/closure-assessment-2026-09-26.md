# 训练恢复系统完整闭环评估

日期：2026-09-26。审查基线：0.2.1／`01e5579`。范围：现有代码、配置、测试、原始实验与报告；本机复现恢复证据和 wheel 身份边界。已完成结果与尚需资源的门槛分别列出。

## 结论与目标边界

现有系统对**单机、固定两个 rank、确定性 map-style 数据、同版本同运行时**的 CPU 恢复，已经形成可重复的功能链：更新边界、DCP 保存、应用层提交、故障检测、清理、候选回退、状态加载、精确比较、负面控制和持久化实验。0.2.1 的完整测试为 99 通过、4 项 CUDA 跳过；实际 300 更新故障恢复与参考运行精确一致。见[完整升级验收](../experiments/full-upgrade-2026-09-26.md)和[0.2.1 复验](../experiments/local-hardening-2026-09-26.md)。

“全面闭环”需要定义为**一个具体支持范围的所有故障路径都能判定、恢复、复核并留下可追溯证据**。目前不能把 CPU 结果推广到实际 GPU、多节点、远程对象存储或断电。这些是新的实现和环境验收，不是补充几条单元测试即可关闭。任意第三方训练脚本、Iterable 数据集、弹性 world size 和跨版本检查点迁移，也不在现有格式 2 契约内。

当前 `trainer.py` 直接构造 `TinyTransformer`、AdamW 和余弦调度器。因此它是一个可信的**恢复实验与验收基座**，还不是可直接接入任意模型的训练框架。若“全面”包括真实任务上线，需要一个明确的训练适配接口：模型／优化器／调度器／数据游标及 RNG 的状态提供器，稳定的更新边界与样本标识，再用一项代表性真实任务重做正面、负面和故障验收。不能仅替换模型名称就沿用现有 CPU 实验结论。

## 本机审查发现

### 1. 恢复决策到实际加载的证据尚未接上

`controller.py` 记录所选候选和恢复行；`trainer.py` 记录各 rank 的 `state_loaded`、`training_started`；但 0.2.1 的 `completion_errors()` 没有逐项核对这些记录。定向复现中，删去成功恢复尝试的 rank 0 `state_loaded` 行后，`validate_runs()` 仍返回通过。最终状态相同可以证明该工作负载的结局，却不能单独证明审计链上“所选检查点由每个 rank 加载”。

本轮实现的修订检查：尝试与恢复决策一一对应；来源尝试、候选路径和更新边界一致；有进展的恢复尝试每 rank 恰有一次加载与训练开始记录；加载更新、消费游标及训练开始的候选路径与决策一致。失败尝试若在加载后、训练开始前退出，仍允许下一次恢复。该检查仍属于**应用自身证据的一致性校验**，不提供抗恶意篡改的签名证明。

### 2. 源码目录与 wheel 的来源指纹不一致

0.2.1 的 `source_sha256()` 把仓库根目录下的 `pyproject.toml` 和 `uv.lock` 算入指纹。打包后这两个文件通常不在包目录，实际复现：同一份 0.2.1 源码在源码树中为 `277fc902…`，从 wheel 单独导入为 `0b09fe6d…`。安装的 wheel 可运行，但相同代码会有不同的来源身份；在包内或临时目录下还可能把不可判定的 Git 状态误报为“干净”。

本轮修订把来源指纹限定为包内 Python 文件，以实际 Python／依赖版本作为单独的恢复兼容条件，并增加 wheel 解包导入检查。旧运行的原始证据不修改；来源算法变化后的检查点依既有严格规则重新生成。

### 3. 跨运行比较原先未核对软件身份

0.2.1 的 `validate_runs()` 检查工作负载指纹及最终状态，但没有比较两个运行保存的源码、Python、PyTorch 与直接依赖版本。`resume()` 已检查这些字段，跨运行比较也应保持同一边界。本轮为格式 2 运行加入环境身份比较；不同来源或运行时会返回明确的不一致诊断。历史无格式 2 元数据的测试夹具仍仅按其旧契约检查。

### 4. 保存提交失败必须通知所有 rank

0.2.1 的 `finish_save()` 由 rank 0 执行 `commit_checkpoint()`，随后广播结果。若提交阶段抛异常，其他 rank 会停在广播，直到进程组超时。双 Gloo rank 注入 `OSError` 后复现：另一个 rank 收到 8 秒通信超时，而不是原始 I/O 错误。本轮修订先广播成功／失败；失败时广播原始错误描述，各 rank 及时退出，rank 0 保留异常因果链。双 rank 回归通过且没有提交成功标记。实际文件系统的 ENOSPC／EIO／只读与断电仍需指定 Linux 环境注入；此处证明的是应用层错误协调。

## 分层验收门槛

| 层级 | 完成判定 | 当前状态 |
| --- | --- | --- |
| A：本机功能与证据 | CPU 参考、正负控制、损坏回退、控制器退出续跑、逐 rank 加载链、提交失败协调、静态检查、测试、构建和 wheel 安装身份均通过；原始记录可复核 | 0.2.2 本机故障注入通过；最终完整回归待归档，Linux 自动验证未执行 |
| B：CUDA 固定拓扑 | 两张实卡上 DDP FP32/BF16/FP16、FSDP2 FP32 的完整矩阵，含 RNG、scaler 跳过、故障、退出资源与同环境精确比较 | 代码已写，实卡证据缺失 |
| C：Linux 本地耐久性 | 指定文件系统和挂载；逐发布边界进程退出、I/O 故障、独立断电／重启后候选选择与回退 | 文件／目录同步已写；断电证据缺失 |
| D：远程存储 | 不可变 generation、全部 payload 验证、有条件 manifest 提交、缺失／损坏／部分删除／凭据及网络失败验收 | 契约已写，服务及实现未选定 |
| E：固定多节点 | 调度器管理整个工作组；旧 attempt 隔离后才启动新 epoch；旧控制者和旧 worker 不可提交；双节点故障／分区／重启矩阵 | 契约已写，实际实现和环境缺失 |
| F：性能与运营 | 预先固定 RTO、最大回滚、容量及额外开销目标；专用主机独立两批每模式至少 12 次，原始值与失败保留；失败能重新进入诊断和修复 | 本机观察可用，稳定性及目标未封板 |
| G：真实任务接入 | 固定一项代表性模型和不可变语料；完整状态提供器；参考／恢复／负面控制与实际吞吐、内存、数据一致性 | 当前只有 tiny 模型和示例 token 数据，尚未选定真实任务 |

官方资料支持这些边界：PyTorch 将异步保存的 staging 与 upload 暴露为不同完成阶段，要求修改模型前保证 staging 完成；[异步 DCP 教程](https://docs.pytorch.org/tutorials/recipes/distributed_async_checkpoint_recipe.html)。`torchrun` 文档说明多节点 agent／node 失败交由作业管理器处理，重启后的 rank 不保证稳定；[弹性启动说明](https://docs.pytorch.org/docs/stable/elastic/run)。Linux `fsync()` 文件并不必然持久化包含它的目录项；[fsync 手册](https://man7.org/linux/man-pages/man2/fsync.2.html)。若选 S3，条件写可用于防止覆盖，但仍须处理 412／409、multipart 和删除竞争；[S3 条件写文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)。这些资料说明所需机制，不替代项目实测。

## 执行顺序与退出规则

1. **先关本机证据链。**恢复加载、跨运行身份、wheel 身份和 rank 0 提交失败协调已完成。接着归档最终完整回归，并在 Linux runner 实际执行自动验证工作流；针对所选文件系统补齐实际 I/O 错误测试。任何测试失败都保留原始运行目录和诊断。
2. **冻结支持范围和 SLO。**按工作负载固定设备、拓扑、数据接口、存储、版本，以及允许的 RTO、回滚窗口、容量和额外训练开销。无预设目标的性能数字只作观察，不作验收。
3. **先实卡及真实任务，再远程存储，最后多节点。**GPU 和代表性任务先确认完整状态及精确恢复；远程存储先做单机事务；多节点最后结合调度器与 fencing。每一层保存独立参考、故障、负面控制和原始指标。
4. **设置发布总闸。**每个门槛至少记录状态（通过／失败／资源阻塞）、源码与运行时身份、配置与数据指纹、环境、测试命令、原始产物路径和复核日期。任一支持场景没有证据或证据失效，发布结论不得写“全面通过”；已发布结果需要能从产物回溯到对应版本和运行。

固定多节点阶段还需决定 rank 映射：现有数据切片及 RNG 是按逻辑 rank 保存。即使 world size 固定，重启后 rank 可能重排；要么由调度层维持稳定逻辑映射并验收，要么设计显式的状态重映射。弹性 world size、跨版本迁移和任意训练状态接入各自需要新契约，不应混入固定拓扑门槛。
