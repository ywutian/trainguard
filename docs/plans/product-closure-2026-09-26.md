# TrainGuard 商业产品闭环与放行门槛

日期：2026-09-26。状态：产品方案；**尚未达到生产发布条件**。

## 1. 产品决定

首个可销售版本建议定位为部署在客户环境中的 **PyTorch 训练恢复验证与执行组件**。客户继续使用自己的训练代码和计算资源；产品负责检查点事务、恢复决策、受控重启、故障演练、可复核的恢复报告与运维告警。首个付费试点只支持一个冻结组合：PyTorch 2.14、固定规模 DDP、一个客户式训练作业、客户 Kubernetes 集群和一种实际验收的对象服务。FSDP2 单独通过相同矩阵后再列入支持范围。

建议以 AWS S3 保存不可变载荷、以单区域 DynamoDB 的条件更新保存提交指针及单调版本/epoch，作为第一种待验证实现。现有内存协议要求 CAS 修订令牌**即使对象内容变回旧字节也不得复用**；S3 `If-Match` 使用 ETag，不能直接当作满足该契约。实现前必须冻结 HEAD 的 ABA 防护与权限模型，再用真实服务验证 A→B→A、并发接管和未知写响应。其他存储服务分别验收，不以 API 名称推定行为相同。

这是一项**待客户发现验证的产品假设**。首个购买者假设为需要运行高成本、多 GPU PyTorch 训练的 ML 平台团队；预算负责人和可收费价值必须通过付费试点确认。产品的价值主张应落在“故障后恢复了正确状态，并能证明恢复过程和有效进度”，而非单纯“自动重启”。

同类能力已经较强，具体对照如下。表中“机会”是待试点验证的假设，不是已经证明的独有功能。

| 方案 | 官方已提供的相关能力 | 本产品需要验证的机会 |
| --- | --- | --- |
| PyTorch `torchrun` + DCP | 整组重启、分片保存/加载；客户训练脚本需实现状态保存和恢复。 | 独立审计状态覆盖与恢复语义，给出可重复的故障验证报告。 |
| Ray Train | worker/node/driver 级恢复、共享存储、提交与异步验证；训练函数仍需保存/加载状态。 | 验证客户现有任务的样本和优化器进度，并提供跨尝试的可移植验收证据。 |
| SageMaker / HyperPod | S3 检查点、Spot 与集群恢复；HyperPod 弹性训练文档指出，单 epoch 作业在故障后以不同 world size 恢复且未保存 dataloader 状态时，已处理样本可能重读。 | 对不同客户数据流显式证明或拒绝“无重复/精确恢复”声明。 |
| SageMaker HyperPod checkpointless | AWS 已在真实 Llama-3 70B 训练中公布逐步 loss 位级一致和 checksum 对照，以及不同 GPU 规模恢复时间。 | 必须以客户现有栈为基线验证接入与独立审计价值；逐步等价本身不是首创。 |
| NVIDIA Megatron Bridge | 故障恢复、异步与本地复制检查点；Energon 已保存 dataloader 状态，且生态中有故障注入矩阵。 | 对已有框架提供独立发布门禁和证据交换；具体差异需客户对照验证。 |
| Determined | 训练平台及现有 Transformers 回调，能上传检查点、处理抢占并自动恢复。 | 在不替换客户整套训练平台的前提下交付验证与审计。 |

因此，不能以“独有自动恢复”“首次保存数据状态”或“所有工作负载精确一致”销售。产品差异必须在**客户既有作业接入、完整训练状态契约、故障演练、恢复正确性证据和跨尝试审计**上由试点实际证明。

## 2. 现状与不可跨越的证据边界

| 链路 | 当前证据 | 产品缺口 |
| --- | --- | --- |
| 本机实验 | 两个 Gloo rank 的实际训练、检查点、故障、回退、精确比较；138 项测试通过、4 项实卡测试跳过，CPU 验收 10/10。见[本机报告](../experiments/simulation-closure-2026-09-26.md)。 | 当前结论只覆盖固定实验任务与本机模拟。 |
| 客户训练接入 | `trainer.py` 固定 `TinyTransformer`、AdamW、Cosine 调度器和 token 数据流。 | 无稳定 SDK、客户状态适配和真实客户训练作业验收。 |
| 远端存储 | `remote_protocol.py` 是内存对象/隔离模型；桥接测试手工搬运真实 DCP 字节。 | 生产 `checkpoint_io.py` 仍读写本地路径，无对象服务适配和远端恢复接线。 |
| 跨主机接管 | 本地控制器使用 `flock`、SQLite、本机进程身份和 `--nnodes=1`。 | 无多节点调度、持久 fencing epoch、独立隔离权威和两主机验收。 |
| 交付运维 | 0.3.1 候选包已有仓库外锁依赖安装/运行/卸载脚本、N/N−1 拒绝与旧版恢复演练、白名单诊断、试点模板和阻断式发布门槛；本机同版证据归入[本地验证记录](../commercial/evidence/local-validation-0.3.1.json)。 | 无客户目标环境安装/升级/回滚、运行监控和值班实测、权限边界与付费试点记录。 |

目前没有可用的实卡、多主机、选定对象服务或受控断电环境。上表的开放项在这些环境中取得原始证据前，始终保持未通过。Git 提交、单元测试和内存模拟不能替代生产放行证据。

## 3. 首个受支持合同与客户接入

发布时必须把以下内容写成版本化 `RunSpec`，由 CLI/API 同一验证器解析：镜像摘要、源码/依赖指纹、PyTorch/CUDA/驱动版本、固定 rank 与设备映射、数据源版本、状态适配器版本、检查点存储位置、保留与容量预算、重启次数、恢复超时、验证目标及证据保留期。恢复不得静默更改这些字段。

客户训练入口通过 SDK 或框架回调登记：模型、全部优化器、调度器、AMP scaler、每 rank RNG、已完成优化器更新、已消费数据位置、数据加载器/增强状态，以及用户定义的状态。保存仅发生在完整优化器更新边界；加载发生在任何新训练步骤之前。适配器必须提供进度与健康信号、数据消费证据和无副作用的状态验证入口。客户提供状态清单、数据流与外部副作用声明，接入审查和针对性漏项负控核实声明。预检只能检查**已登记**的状态；未审查部分记为 `UNVERIFIED`，不得凭预检授予精确结论。

单个生产作业的报告记录**本次可直接验证的事实**，避免把哈希等同于训练正确性：

1. **结构完整**：所有 rank 的对象、大小、摘要、manifest、版本与来源一致，DCP 能解码和加载。
2. **进度一致**：恢复后的优化器更新、已消费批次、数据位置和相关状态与选定边界一致；旧尝试的无效进度不计入完成量。

另为**工作负载 × 环境 × 产品版本**签发验收结论，只有完整 campaign 才能授予：

1. **精确复现**：在同一受支持运行时、设备拓扑和不可变数据上，独立参考与故障作业的有效样本序列和最终训练状态逐项一致，负面控制被拒绝。
2. **生产韧性**：真实设备、对象服务、调度器和节点故障矩阵已通过，且升级/回滚与告警演练完成。

每份作业报告应引用对应的验收版本、环境指纹和证书，明确本次事实与历史验收的区别。PyTorch 官方说明不同版本、平台及 CPU/GPU 间不能普遍保证逐位一致；非确定性算子或客户自定义数据流水线需明确验证范围与容差，不能领取“精确复现”结论。

## 4. 同一个端到端事务

```mermaid
flowchart LR
    A[提交客户 RunSpec] --> B[预检与状态适配]
    B --> C[调度固定工作组]
    C --> D[完整更新边界保存]
    D --> E[各 rank 不可变对象]
    E --> F[清单校验与强一致条件发布]
    F --> G[故障检测与旧组隔离]
    G --> H[新 epoch 选择最新有效版本]
    H --> I[全组加载并继续]
    I --> J[有效进度及状态验证]
    J --> K[证据报告、告警与计量]
```

控制器必须是唯一重试决策者。调度器只负责资源与进程生命周期；**强一致提交权威**保存检查点有效性及单调 epoch，运行索引可以重建。每个 attempt 带 epoch；接管先证明旧工作组退出或由独立权威确认隔离，再激活新 epoch。发布和最终完成必须经**服务端条件写与权限**验证当前 epoch，不能只信任进程内 `authority.require`。旧 epoch 已在途载荷可以成为不可见孤儿，但旧 actor 不得发布有效检查点或完成声明；其外部副作用须另行约束。失联节点是否仍在运行不能仅由 Pod 删除状态推断。网络分区时若无法证明隔离，状态进入 `BLOCKED` 并告警，不启动可能并存的有效 attempt；恢复旧节点网络后实测拒写。

对象存储使用不可变 generation、逐对象摘要及所有 rank 的完整清单；单区域强一致提交权威用单调版本与条件更新发布指针，禁止删除或复用活跃 HEAD。HEAD 至少包含 `revision`、`epoch`、`operation_id` 和 manifest 摘要；创建检查键不存在，更新同时检查预期 revision 与 epoch 并递增 revision。写入响应丢失时，对 HEAD 做强一致读回并核对 `operation_id`，不能仅凭超时重写。工作进程只获其 generation 载荷写权限，不得更新 HEAD。条件写冲突、限流、部分多段上传、凭据过期、对象损坏和保留删除中断都需要明确的幂等读回/重试/回退动作。S3 的单对象原子性与条件写入不等于多对象事务，也不自动给出永不复用的修订令牌；提交协议和实际服务故障注入共同定义产品保证。DynamoDB 全局表采用冲突调和，不能未经额外证明就用于这个单调 CAS 权威。

检查点与证据必须有明确的信任边界：只加载受信任作业身份在授权命名空间中发布的对象，服务端拒绝跨作业路径和越权发布；哈希检测损坏，不证明作者身份或防止有写权者同步伪造 manifest。若对客户承诺独立防篡改审计，须采用独立写入身份及签名或不可变证据存储。DCP 元数据可能触发反序列化，禁止加载不可信来源。

外部副作用是单独的接入条件：若客户训练步骤会写外部数据库、消息队列或业务 API，适配器须声明幂等键或由客户提供事务/补偿措施；仅恢复模型参数不能保证这些副作用恰好发生一次。

## 5. 一次性纵向切片的实施顺序

“一次性闭环”应指**同一真实客户样例贯穿全部环节并只在完整验收后发布**，而不是先发布局部能力再补上可靠性承诺。下面的工作可并行开发，但每项都汇入同一个版本、同一组验收证据。

| 工作包 | 可交付接口与实施内容 | 必须出现的通过证据 |
| --- | --- | --- |
| A 客户作业 | 从固定示例训练器抽出版本化状态适配 SDK；首个试点提供一个非内置 PyTorch DDP 作业、状态清单与数据流声明。对已声明状态做结构预检及接入审查，未登记范围记 `UNVERIFIED`。 | 同一客户式作业的无故障参考、故障恢复、漏 RNG/优化器/数据位置负控，在 CPU 与实卡各跑通。FSDP2 独立扩展。 |
| B 持久存储与发布 | 实现 S3 不可变对象 adapter、独立强一致 HEAD/epoch 权威和真实凭据权限；把保存/选择/加载接入生产训练路径；建立对象布局、保留和恢复期间 lease。 | 真实 S3 与权威服务上覆盖条件冲突、A→B→A、未知响应、坏对象、旧版本回退、限流、凭据过期、旧身份拒写和部分删除。 |
| C 工作组接管 | 选择客户 Kubernetes 作业控制方式，定义单一控制器、节点状态与独立隔离权威；禁用重复的自动重试所有权。隔离无法证明时失败关闭。 | 两台真实主机上 worker/node/控制器失效、网络分区、旧控制器复活；旧节点重新连网后不能发布，恢复结果正确。 |
| D 验证和性能 | 将参考/故障/负控、样本序列、状态摘要、回滚步数、RTO、RPO、保存开销和资源峰值纳入同一 campaign。 | 同一镜像/数据/拓扑多次运行；预先冻结场景次数、观测窗口、RTO 起止点、超时计入规则、统计方法和阈值，保留失败与原始值。 |
| E 安全与运维 | 生产模式关闭故障注入和故意漏状态开关；工作负载身份和最小权限、传输/静态加密、秘密轮换、信任边界、日志容量/保留；默认监控不记录原始样本 ID；指标、集中日志、告警、值班处置。 | 授权篡改、跨作业访问与权限拒绝测试；磁盘/存储额度和告警演练；高步数证据写入开销、安装、升级、回滚、备份恢复和故障手册实际演练。 |
| F 包装与商业 | 固定部署包、SBOM/构建来源/版本兼容矩阵、安装器及诊断包；合同边界、支持时段、报价和付费试点流程。 | 客户环境安装和卸载演练、N/N−1 检查点与控制协议兼容/回滚演练、试点签收、实际价值测量、支持流程与商业条款审核；不能宣称未达到的供应链认证级别。 |

代码实施的关键路径为 **A → B → C → D → E/F → 同一环境整体验收**。B 与 C 的接口可以同时设计，但没有 A 的真实客户式作业，后续再多模拟都不足以证明可销售承诺。现有内存协议、CPU campaign 和故障矩阵应复用，不应重写历史证据。

| 商业试点 | 至少一个真实客户签收付费试点，并按客户原始 GPU/工程工时账本核算可归因价值；范围、支持、责任与付款条款已审核。 | 未完成；尚无客户证据 |

报告必须列明 `PASS`、`FAIL` 或 `BLOCKED` 和证据路径；缺少环境或记录为 `BLOCKED`，不得折算为通过。对客户展示的“可用”状态只来自上表全绿的特定版本、环境和作业等级。

商业阶段分三道边界：**有限付费接入研究**可在本机包与 CPU 门槛通过后，以 `EVALUATION_ONLY` 包和明确研究工作说明书进入客户隔离环境，逐项写明未实现能力、失败/阻断归因、费用和退出条件，不承诺生产自动接管；**客户环境受限技术验收**是在该合作中对冻结的一个 DDP 客户作业、版本、实际拓扑与对象服务跑全矩阵并由双方签收，只有实际通过的范围可称已验收；**广泛商用发布**还需付费试点结果、公开支持矩阵扩展复测、可运营的安全与支持机制及持续 SLO/事故证据，才能承诺公开执行的服务等级。试点合同不得把尚未验证的 FSDP2、其他拓扑或多租户能力列入支持范围。故障矩阵正确性要求零错误；少量演练不能直接推算线上可用率或通用 SLA。

## 7. 价值证明与首单包装

建议先销售**客户环境部署的有限付费审计/接入试点**：固定接入一个训练作业、一个集群、一个对象服务，交付恢复正确性报告、故障演练结果、部署/回滚手册和约定支持时段。当前代码采用 MIT 许可，现有代码的使用权不能再包装为排他性年度软件许可；试点费用应对应明确的接入、验证、报告与支持服务。只有另行开发并经权属与法律审核的新增专有组件，才可在未来另列许可条款。年度阶段可对已验收的工作负载族和环境提供持续复测、适配与支持订阅；并发 GPU/作业数可作为容量参考，但定价须由客户采购访谈与成本账本校准。若采用按受保护时长计费，只有作业处于支持矩阵内且存在可验证、未过期的可恢复检查点时才计入；需建立可重放、可去重、可对账的内部计量记录。避免在缺少实测前宣称固定节省比例或通用 RTO。

每次试点记录：故障前基线、故障次数和原因、GPU 单价、有效回滚 GPU 小时、首次恢复更新的 RTO、保存/存储额外开销、平台工程师处置时间。可归因净价值 = 相对**客户原有恢复方案**避免的重跑计算与人工处置成本 − 产品引入的计算、存储、运维、许可和服务费用；对无故障窗口也应报告净开销。客户原有 Ray、SageMaker、NVIDIA 或 Determined 能力应作为对照基线，不以“从零恢复”夸大收益。

商业操作按同一试点记录形成可复核链条：采购访谈和原始成本基线 → 约定范围/阈值/报价 → 客户环境安装与演练 → 双方验收 → 发票与支持交接 → 定期复核节省价值、事故和续约意愿。没有真实客户报价/付费/签收证据时，只能称为产品假设，不能称为已验证市场需求。

在试点前取得客户对以下条件的书面确认：支持环境、数据与检查点归属、访问和保留期、故障注入窗口、验收阈值、事故升级联系人、维护窗口、支持级别、责任限制及许可文本。法律和采购条款需由相应专业人员审核；技术报告不能代替合同。

## 8. 可在当前机器完成的工作与外部输入

现在可完成：SDK/状态契约设计与 CPU 接入、生产/实验模式隔离、报告等级和拒绝规则、对象服务 adapter 的接口和确定性故障测试、部署清单模板、指标/日志 schema、构建来源与本地升级/回滚演练。每项都应在同一候选版本上保留失败用例和原始证据。

结束发布阻塞至少需要：一个真实客户式 DDP 训练作业及其完整数据/状态声明；两张以上实际 GPU 和两台主机；选定的 Kubernetes、S3 与强一致提交权威及可测试凭据；受控故障/断电环境；一个愿意定义验收与付费试点的设计伙伴。资源到位后，先冻结客户作业/版本/拓扑/阈值，再运行同一整体验收入口，修复直到全部门槛通过。
